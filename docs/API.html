POST
/api/cbi/assessments
CBI 응답 제출 · 점수 계산
{ "round": "INITIAL", "questionnaireVersion": "cbi-ko-2026.11.2", "answers": [{ "no": 1, "option": 1 }, { "no": 2, "option": 0 }] }
  • 요청에 questionnaireVersion을 필수로 포함합니다(문항 조회의 version). option은 보기 순서(0~4). 서로 다른 번호 1~13의 응답을 정확히 13개 보내며 중복·누락·버전 불일치는 400. 역문항·환산은 해당 문항 버전으로 서버가 처리합니다.
  • round: DAY28은 dayIndex ≥ 28일 때만(아니면 409 CBI_NOT_DUE). 같은 회차 두 번은 409 CBI_ALREADY_TAKEN.
  • MVP의 round는 INITIAL·DAY28만 허용합니다. FOLLOW_UP은 미지원입니다.
  • 응답 201:
{
  "id": 5, "round": "INITIAL", "takenAt": "2026-11-03T21:02:00+09:00",
  "personal": { "score": 62.5, "level": "HIGH" },
  "work": { "score": 55.4, "level": "HIGH" },
  "highRisk": false,
  "safety": { "show": false },
  "onboardingStep": "LIFESTYLE"
}

  • level: LOW(50 미만) HIGH(50 이상 75 미만) VERY_HIGH(75 이상). 이는 프로젝트 표시 기준이며 진단을 뜻하지 않습니다. highRisk(어느 하나 75 이상)면 safety.show: true → C3 안전 안내를 띄웁니다.

  • 검사 순서: 로그인(401) → 건강정보 동의(403 HRV_CONSENT_REQUIRED) → 형식 검증(400) → 회차 조건(409) → 재시도 키. INITIAL은 프로필 단계를 마친 뒤(onboardingStep이 PROFILE이면 409 ONBOARDING_STEP_INVALID) 제출하며, 현재 단계가 CBI일 때만 LIFESTYLE로 전진합니다(이미 지난 단계는 되돌리지 않음). DAY28의 응답 onboardingStep은 현재 단계(DONE)입니다.

  • 점수는 DB에 소수 둘째 자리(DECIMAL 5,2)로 저장하고, 응답은 소수 첫째 자리로 반올림합니다. level은 저장값으로 판정합니다.

  • 구현 해석(확인 필요) CBI_HIGH 안내는 가장 최근 CBI 기준입니다. high_risk인 응답마다 새 안내를 만들고(같은 사용자의 열린 CBI_HIGH는 해제 후 대체), high_risk가 아닌 응답은 열린 CBI_HIGH를 해제(resolved_at)합니다.

3. 홈 (B1)

GET
/api/home
오늘 회복 · 이번 주 부하 · 추천 요약

홈에 필요한 값을 한 번에 줍니다.

{
  "nickname": "아리", "dayIndex": 9, "phase": "ESTABLISHED",
  "todayCheck": { "status": "DONE" },
  "recovery": {
    "status": "LOW", "changePct": -6.0,
    "baseline": { "validDays": 9, "required": 7, "established": true },
    "conditionScore": 3, "excludedToday": false
  },
  "thisWeekLoad": { "vsUsualPct": 18.0, "riskLevel": "WATCH" },
  "judgment": "OVERLOAD_LOW",
  "todaySuggestions": [ "Suggestion" ],
  "safety": { "show": false },
  "plan": { "plan": "TRIAL", "daysLeft": 20 }
}
  • phase: BUILDING(적격 측정 7일 미만) / ESTABLISHED(7일 확보 후). dayIndex와 구분합니다. 빠짐없이 유효 측정했다면 7일차 체크 완료 후 리포트가 열리고, 누락·교란·품질 실패가 있으면 늦어질 수 있습니다.
  • todayCheck.status: NOT_STARTED IN_PROGRESS DONE → NOT_STARTED면 "측정하러 가기"를 위에 크게.
  • recovery.status: BUILDING NORMAL LOW INSUFFICIENT. 0~100 회복 점수는 쓰지 않고 "평소 대비 %"(changePct) + 상태로 표시합니다(예: "평소보다 6% 낮아요").
  • judgment: OK OVERLOAD_OK OVERLOAD_LOW NORMAL_LOW BUILDING INSUFFICIENT. 기준선이 있어도 최근 자료가 부족하면 INSUFFICIENT이며 HRV에 근거한 LOW/NORMAL 판단을 하지 않습니다.
  • 온보딩 완료 후에만 조회합니다(403 ONBOARDING_REQUIRED). 읽기 전용이라 회복 상태·추천을 계산하거나 만들지 않습니다.
  • todayCheck.status: 오늘 체크가 없으면 NOT_STARTED, 있으나 컨디션 전이면 IN_PROGRESS, 컨디션까지 저장했으면 DONE.
  • todaySuggestions: 오늘 날짜(targetDate)의 PRE_START·RECOVERY 제안 중 DISMISSED EXPIRED UNDONE을 뺀 것(시작 시각 순).
  • 구현 해석(확인 필요) recovery.status·changePct·baseline은 오늘 이하에서 가장 최근 회복 상태 기준입니다(오늘 기록 전이면 어제까지 계산값). 기록이 없으면 BUILDING. excludedToday는 오늘 컨디션까지 입력했는데 적격일이 아닐 때(교란 요인·대표값 없음) true입니다.
  • 현재 구현 범위: thisWeekLoad(schedule 읽기 계약)·plan(subscription 읽기 계약)은 일정축 계약이 생기기 전까지 null, judgment는 추천 임계값 확정 전까지 null입니다.

POST

활동 수행 완료 체크
  • 상태 규칙: PROPOSED → APPROVING → APPROVED; PROPOSED → DISMISSED/EXPIRED; 확정 등록 실패만 APPROVING → FAILED(재시도는 FAILED → APPROVING). 타임아웃은 FAILED로 확정하지 않습니다.
  • dismiss는 PROPOSED에서만, undo는 APPROVED에서만 허용합니다. undo는 앱 소유 Google 일정임을 확인하고 삭제 후 UNDONE(이미 삭제된 404도 성공). done은 APPROVED에서 일정 종료 후 허용하고 doneAt만 채우며 상태는 유지합니다. 완료한 일정은 undo 불가입니다. 반복 dismiss/undo/done은 같은 결과 200, 그 외 전이는 409 INVALID_STATE입니다.
  • generate는 기존 APPROVED를 보존하고 미승인 중복을 만들지 않습니다. 모든 갱신 응답은 최신 Suggestion입니다.
  • 조회·건너뛰기·했어요는 로그인 사용자 본인 제안만 다룹니다(남의 id는 404). type=RECOVERY 조회는 온보딩 완료 후(403 ONBOARDING_REQUIRED), PRE_START는 온보딩 중에도 조회합니다. type·status가 정의된 값이 아니거나 date가 YYYY-MM-DD가 아니면 400입니다. 목록은 시작 시각 순입니다.
  • done을 일정 종료 전에 부르면 409 INVALID_STATE("일정이 끝난 뒤에 체크할 수 있어요.")입니다. message는 문구가 없으면 null입니다.
  • 제안의 등록 키(registration_key)는 생성 때 서버가 만드는 Google event id(cd + 32자, base32hex 문자만)이며 응답에 내보내지 않습니다. 승인 시작 때 같은 사용자의 다른 APPROVING·APPROVED 예약과 겹치면 409 SLOT_CONFLICT입니다. 만료 시각이 지난 PROPOSED는 서버가 주기적으로 EXPIRED로 바꿉니다.
  • 현재 구현 범위: relatedEvent는 calendar 읽기 계약(일정축)이 생기기 전까지 null입니다. RECOVERY 추천 생성은 "1~7일 컨디션 기반 추천 임계값" 확정 후 구현합니다.

  • 아래 상태 코드가 생략된 갱신 요청은 200, 본문 없는 삭제·로그아웃·동의 변경은 204입니다. 컬렉션은 빈 배열, 계산 불가 값은 null. 400의 fieldErrors 등 조건부 필드는 예외입니다.
  • 시각 범위는 [start, end)이며 start < end. 조회의 날짜 to는 포함하되 내부적으로 다음 날 00시 미만으로 변환합니다. 종일 일정은 startDate, endDateExclusive도 반환합니다(서울 시간 정규화). 종일 일정의 부하 가중치는 미확정이며 임의로 24시간으로 계산하지 않습니다.
  • vsUsualPct와 내 범위 위치는 분모가 0이거나 표본이 부족하면 null + unavailableReason(NO_BASELINE, ZERO_BASELINE, INSUFFICIENT_DATA, POLICY_PENDING)입니다. 내 범위 최고=최저인 경우도 null(INSUFFICIENT_DATA). 위치는 유효할 때 0~100으로 제한합니다.
  • 일정 부하(load-v1)·회복 계산(recovery-v1)·2주 연속 낮음·내 범위 위치의 산식은 계산_정책.md로 확정했습니다. 모든 수치는 초기값이며 결과 행의 calculation_version으로 버전을 남기고 실제 데이터를 보며 조정합니다. POLICY_PENDING/422 CALCULATION_POLICY_PENDING은 앞으로 새로 추가되는 미확정 정책에만 씁니다.
  • POST 측정 저장·CBI 제출·추천 생성·승인에는 Idempotency-Key(UUID)를 필수로 보냅니다. 사용자+작업+키를 고유하게 저장하고 본문 해시와 결과를 비교합니다. 같은 키·같은 본문은 원래 결과, 같은 키·다른 본문은 409. 키 보관은 최소 24시간입니다. 측정 재측정은 새 키입니다.
  • 추천 승인 시 사용자별 잠금으로 중복 승인과 겹친 승인을 직렬화하고 Google의 최신 빈 시간을 재확인합니다. 동일한 Google event id로 재시도하며 타임아웃은 조회로 확인합니다. 외부 앱이 확인 직후 일정을 추가하는 경합까지 막을 수는 없습니다.
  • onboardingStep은 서버가 전진시킵니다. 프로필·초기 CBI·생활 정보·캘린더 권한 및 일정 분석 결과가 선행 조건이며 /onboarding/complete에서 다시 검사합니다. 동기화 성공+일정 0건도 완료 가능합니다. 설정 수정은 완료된 온보딩을 되돌리지 않습니다.
  • CSRF 쿠키는 로그인·로그아웃 후 다시 발급받습니다. 읽기용 GET은 데이터 동기화·추천 생성 같은 도메인 변경을 하지 않습니다.
