## 3. 프론트·운영에 알릴 것

- **온보딩(#30)**: A5 "홈으로" 전에 캘린더 연결과 `POST /api/calendar/sync` 성공이 필요하다. 건너뛰면 409다.
- **local 개발(#30)**: `GOOGLE_CLIENT_ID` 없이 실행하면 API로 온보딩을 완료할 수 없다. `POST /api/dev/seed` 데모 계정을 쓰거나 Google 설정을 넣는다.
- **동기화(#32)**: 프로필 저장(동의 기록) 전에 동기화를 부르면 409다. `user_consents`에 `CALENDAR` 행이 없는 기존 테스트 계정도 409가 된다. 새로 시드하는 데모 계정은 동의가 함께 들어간다.
- **탈퇴(#33)**: 202로 끝나도 세션이 끊기고 쿠키가 지워진다. 프론트는 202도 로그아웃 상태로 처리한다.
- **승인(#31, #37)**: 확인 중인 제안을 다시 승인하면 `FAILED` 대신 202 또는 오류 + `APPROVING` 유지가 될 수 있다. 제안한 시간 그대로 승인해도 그 사이 일정이 생겼거나 시간이 지났으면 409 `SLOT_CONFLICT`가 온다("다른 시간 보기"로 안내).
- **부하 점수(#29, #35)**: 주말 밤 일정이 있는 주의 점수가 낮아진다. 분류기가 생겨 운동·약속·개인 일정은 부하에서 빠지고 시험·발표는 1.5배와 마감 수에 반영된다. 이미 저장된 값은 다음 동기화가 범위(이번 주 −4주 ~ +5주)를 다시 계산할 때 바뀐다.
- **캘린더 연결(#38)**: 로그인한 채 다른 구글 계정으로 캘린더를 연결하면 `/?authError=true`로 돌아온다. local에서 테스트 로그인으로 들어간 데모 계정은 실제 구글 계정과 식별자가 달라 그 세션에서는 연결이 거부된다(로그아웃한 뒤 캘린더 연결 주소로 들어간다).
- **환경 변수(#38)**: `GOOGLE_CLIENT_ID`를 설정하면 `GOOGLE_CLIENT_SECRET`과 `COMEDOWN_TOKEN_KEY`가 모두 있어야 서버가 시작된다.
- **프록시 뒤 배포(#39)**: 로드밸런서·Cloud Run 뒤에서는 운영 환경 변수에 `SERVER_FORWARD_HEADERS_STRATEGY=framework`를 넣는다. 앱이 프록시 없이 직접 노출되는 구성에서는 켜지 않는다.
- **구글 콘솔**: 백엔드는 로그인과 캘린더 연결에 리디렉션 주소를 따로 쓴다. `/login/oauth2/code/google`과 `/login/oauth2/code/google-calendar`를 백엔드(8080)·프론트(5173)·운영 주소마다 모두 등록해야 한다.

## 4. 고치지 않은 지적

정책이나 구조 결정이 먼저 필요하거나 스키마 변경이 필요한 항목이다.

**결정이 필요한 것**
- #23 `calendar.application`이 `schedule.contract`에 의존하고 schedule은 `calendar.contract`에 의존한다(양방향). 책임 매핑은 `GET /api/calendar/events`를 calendar.api 소유로 두는데 응답에 `week: WeekLoad`가 필요해 생긴 문제라, 조합을 experience로 옮길지 매핑을 바꿀지 정해야 한다.
- #18 동기화 전이라 행이 없는 직전 주를 0으로 넣어 평균을 내면 첫 동기화 직후 일부 주가 `LOAD_HIGH`로 나올 수 있다(Q8 임시 해석과 일치). → 2026-11-17 확정: 기록이 없는 주는 0으로 본다(지금 구현 유지).
- #23 제목 해시가 토큰 암호화 키를 함께 써서, 키를 바꾸면 제목 단위 분류 규칙이 맞지 않게 된다. 키를 나누면 기존 규칙이 무효가 된다.
- #27 연결 해제 후 재연결하면 일정이 새 id로 만들어져 같은 마감에 제안이 하나 더 생길 수 있다. 마감을 식별할 기준이 필요하다.
- 배포 구성: 프론트와 API를 같은 출처로 제공해야 한다(CORS 설정 없음, 세션 쿠키 `SameSite=Lax`). Firebase Hosting의 rewrite 뒤에 API를 두면 `__session` 외의 쿠키가 지워져 로그인이 유지되지 않는다(README "프록시 뒤에 배포할 때").

**스키마 변경이 필요한 것**
- #26·#27 정리 재시도와 승인 재확인의 횟수 제한·늘어나는 간격·종료 상태(지금은 실패 건을 뒤로 보내기만 한다).
- #27 되돌리기 도중 "했어요"가 끼어들면 구글 일정은 지워졌는데 되돌리기가 409로 끝날 수 있다("되돌리는 중" 상태가 필요).
- #24 정확한 "마지막 동기화 시각"(전용 컬럼이 필요).

**메모**
- #28 동의는 유지한 채 건강 기록만 지우는 삭제와 측정 저장이 겹치면 측정 쪽이 오류로 끝날 수 있다(코드 기준, 재현하지 않음).
- #38 철회 대기가 아닌 토큰이 복호화되지 않을 때(키 변경 뒤 동기화) 자격 조회가 500이다.
- AI 일정 분류와 AI 해석 문구는 아직 없다(`ai`, `integration.openai`는 빈 패키지). 규칙에 걸리지 않는 일정은 `OTHER`로 남는다.

**A4·A5·C1-2와 백엔드 대조(와이어프레임 수정 요청사항 2)**
- A4 생활 정보(1-5): 기상 시간 = `measureTime`, 취침·기상 = `sleepStart`·`sleepEnd`, 선호 활동 6개(`WALK` `STRETCH` `NAP` `YOGA` `MEDITATION` `LIGHT_RUN`), 직접 추가 없음 → `PUT /api/me/settings` 그대로.
- A5 일정 리포트(1-6): 쉬는 날·밤 10시 이후·마감 = `pastMonth.restDays`·`lateNightCount`·`deadlineCount`, 지난달 대비 값 없음, 앞으로 4주 = `upcomingWeeks`, 평소 대비 % = `vsUsualPct`, 단계 3개 = `riskLevel`(`NONE` 보통 · `WATCH` 주의 · `RISK` 위험), 0~100 지수 없음 → `GET /api/schedule/report` 그대로. 과부하 제안 문구는 #50에서 보강. "AI 생성" 배지는 AI 문구 생성이 없어 표시되지 않는다(`aiGenerated: false`).
- C1-2 회복 리포트 그래프(1-9): HRV 점·7일 평균·정상 범위와 주차별 부하 막대가 같은 날짜 축(`graph.from`~`to`, `loadWeeks[].weekStart`~`weekEnd`)을 쓴다 → `GET /api/reports/recovery?days=28` 그대로.

**결정을 구현하면서 임시로 정한 것(확인 필요)**은 [계산_정책.md](계산_정책.md) "회복 추천" 절의 구현 해석에 적었다. 특히 화면의 회복 상태 칩은 `recovery-v1` 그대로이고 추천 기준만 지난주 평균 비교라는 점이다.
