# 배포 가이드

백엔드를 컨테이너 이미지로 만들어 배포할 때 필요한 것을 정리한다. 팀은 **GCP Cloud Run + Cloud SQL(MySQL 8.4)** 로 배포하기로 했다(2026-11-17). Cloud Run 절차는 [7. Cloud Run 배포](#7-cloud-run-배포)에 있다. 2026-11-17 GCP에 처음 배포해 서버 기동과 기본 확인을 마쳤다(아래 "확인한 범위").

## 1. 구성

```text
브라우저 ── HTTPS ──> Cloud Run 서비스 1개(https://<서비스>-<프로젝트번호>.<리전>.run.app)
                        └─ ingress 컨테이너(nginx, 8080 — 밖으로 여는 유일한 포트)
                             ├─ /api/**, /oauth2/**, /login/oauth2/**  →  backend 컨테이너(127.0.0.1:8081)
                             └─ 그 외                                    →  프론트 빌드 파일(index.html로 SPA 라우팅)
백엔드 ── Cloud SQL MySQL 8.4 비공개 IP (세션·일정·건강 기록)
백엔드 ── Google OAuth / Calendar API, OpenAI
```

- **프론트와 API는 같은 출처여야 한다.** 백엔드에 CORS 설정이 없고 세션 쿠키가 `SameSite=Lax`다. 프록시의 경로 규칙으로 위 세 경로를 백엔드로 보낸다.
- **Firebase Hosting의 rewrite 뒤에 API를 두지 않는다.** Firebase Hosting은 Cloud Run·Functions로 넘길 때 `__session` 쿠키만 전달하는데, 이 서버는 `SESSION`(세션)과 `XSRF-TOKEN`(CSRF)을 쓴다.
- 백엔드는 프록시를 거쳐서만 닿게 한다. 직접 노출되는 구성에서는 `SERVER_FORWARD_HEADERS_STRATEGY`를 켜지 않는다.
- 세션은 DB(Spring Session JDBC)에 있어 인스턴스가 바뀌어도 로그인이 유지된다.
- **인스턴스는 1개로 고정하고 요청이 없을 때도 CPU가 돌게 한다.** 서버 안에 주기 작업(제안 승인 재확인 1분, 제안 만료, 탈퇴·연결 해제 정리 재시도, 재시도 키 정리)이 있고 인스턴스 간 잠금이 없다. Cloud Run이면 최소·최대 인스턴스를 1로 두고 CPU를 항상 할당하는 설정을 쓴다. 요청이 올 때만 CPU를 주는 기본 설정에서는 이 작업들이 제때 돌지 않는다.

## 2. 이미지

```bash
docker build -t come-down-backend .
```

- 저장소 루트의 `Dockerfile`이 Gradle Wrapper로 jar를 만들고 JRE 21 이미지에 담는다. 테스트는 CI에서 돌리므로 이미지 빌드에서는 돌리지 않는다.
- `.dockerignore`가 `gradlew`·Gradle 설정·`src/main`만 보낸다. `.env`는 빌드에 들어가지 않는다.
- 컨테이너는 **8080 포트**로 HTTP를 받는다(`server.port` 고정). Cloud Run을 쓰면 컨테이너 포트를 8080으로 둔다.
- 프로필을 지정하지 않고 실행한다. `local` 프로필 전용인 `/api/dev/**`(테스트 로그인·시드·날짜 이동)는 운영 이미지에서 켜지지 않는다.

## 3. 환경 변수

| 변수 | 필수 | 내용 |
|---|---|---|
| `SPRING_DATASOURCE_URL` | 필수 | 예: `jdbc:mysql://<호스트>:3306/comedown`. DB와 계정은 미리 만든다(문자셋 `utf8mb4`, 정렬 `utf8mb4_0900_ai_ci`) |
| `SPRING_DATASOURCE_USERNAME` / `SPRING_DATASOURCE_PASSWORD` | 필수 | 테이블 생성 권한이 있는 계정(Flyway가 처음 뜰 때 스키마를 만든다) |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | 필수 | 구글 OAuth 클라이언트. ID만 넣고 비밀번호를 비우면 시작하지 않는다 |
| `COMEDOWN_TOKEN_KEY` | 필수 | 구글 토큰 암호화 키. Base64로 인코딩한 32바이트(`openssl rand -base64 32`). **바꾸면 저장된 토큰을 못 읽어 사용자가 캘린더를 다시 연결해야 한다** |
| `SERVER_FORWARD_HEADERS_STRATEGY` | 프록시 뒤면 필수 | `framework`. 없으면 구글 리디렉션 주소가 `http://`로 만들어져 로그인이 `redirect_uri_mismatch`로 막힌다 |
| `OPENAI_API_KEY` | 선택 | 넣으면 해석 문구(오늘 결과·회복 리포트·28일차 리포트)를 AI가 쓴다. 없으면 규칙 기반 문구만 내려간다. 비밀값이므로 Secret으로 주입한다 |
| `OPENAI_MODEL` | 선택 | 사용할 OpenAI 모델. 비우면 `gpt-4.1-mini`. 응답이 5초를 넘으면 규칙 기반 문구로 대체하므로 빠른 모델을 쓴다 |

- 비밀값은 저장소·이미지·로그에 넣지 않고 배포 환경의 비밀 저장소(GCP Secret Manager 등)로 넣는다.
- DB 스키마는 서버가 뜰 때 Flyway가 맞춘다. `ddl-auto=validate`라 스키마가 다르면 시작하지 않는다.

## 4. 구글 콘솔

- **승인된 리디렉션 URI**에 운영 주소를 두 개 모두 넣는다: `https://<운영 도메인>/login/oauth2/code/google`, `https://<운영 도메인>/login/oauth2/code/google-calendar`.
- **데이터 액세스**에 `https://www.googleapis.com/auth/calendar.events` 범위가 있는지, 프로젝트에서 **Google Calendar API**가 켜져 있는지 확인한다.
- **대상(게시 상태)**: 테스트 상태면 등록한 테스트 사용자만 로그인할 수 있다. 시연에 쓸 계정을 미리 넣거나 프로덕션으로 게시한다.

## 5. 배포 후 확인

1. `GET https://<운영 도메인>/api/auth/csrf` → 204, `XSRF-TOKEN` 쿠키에 `Secure`가 붙는지.
2. `GET https://<운영 도메인>/oauth2/authorization/google` → 구글로 넘어가는 주소의 `redirect_uri`가 `https://<운영 도메인>/login/oauth2/code/google`인지.
3. 실제 계정으로 로그인 → 프로필·동의 저장 → 캘린더 권한 → `POST /api/calendar/sync` 200.
4. `POST /api/dev/login`이 404 또는 401인지(운영에 local 전용 기능이 없어야 한다).

## 6. 시연 대비

- 행사장 네트워크가 불안정할 수 있다. 인터넷 없이도 보여 줄 수 있게 로컬 실행 환경(README "실행")과 데모 시드(`POST /api/dev/seed`, local 프로필)를 준비한다. 구글 로그인·캘린더 동기화는 인터넷이 필요하다.
- 개발 마감 뒤에는 공식 저장소에 커밋할 수 없으므로, 배포 설정 변경도 마감 전에 끝낸다.

## 7. Cloud Run 배포

### 7.1 파일

| 파일 | 내용 |
|---|---|
| `Dockerfile` | backend 이미지 |
| `deploy/cloudrun/ingress/` | ingress 이미지: `nginx.conf`(경로 나누기·전달 헤더), `Dockerfile`, `placeholder/`(프론트 없이 배포할 때의 확인용 화면) |
| `deploy/cloudrun/service.yaml` | 서비스 정의 틀. `${...}` 자리(프로젝트·DB 주소·클라이언트 ID·이미지 태그)는 스크립트가 채워 임시 파일로만 쓴다. 비밀값은 Secret Manager 이름만 적는다 |
| `scripts/deploy-cloudrun.ps1` | 두 이미지 빌드(linux/amd64) → Artifact Registry push → `gcloud run services replace` → 공개 호출 권한 → 주소 출력 |

서비스 정의의 고정 설정과 이유:

- 인스턴스 최소·최대 1, CPU 항상 할당(`cpu-throttling: false`): 1절의 주기 작업 때문이다. 대신 요청이 없어도 과금된다.
- backend는 `SERVER_PORT=8081`, `SERVER_FORWARD_HEADERS_STRATEGY=framework`. backend 포트는 같은 인스턴스 안에서만 닿으므로 전달 헤더를 켜도 된다. nginx는 `Host`·`X-Forwarded-Host`·`X-Forwarded-Proto`를 넣고, 클라이언트가 보낸 `Forwarded`·`X-Forwarded-Prefix` 등은 지운다.
- `container-dependencies`로 backend가 뜬 뒤(8081 startupProbe 통과) nginx를 띄운다.
- DB는 Cloud SQL **비공개 IP**로 붙는다(Direct VPC egress, 사설 대역만 VPC로). 코드에 Cloud SQL 커넥터를 넣지 않는다.
- 요청 제한 시간 120초(nginx `proxy_read_timeout`과 같다). 요청 본문은 10MB까지(HRV 원신호).

### 7.2 GCP 준비(한 번만)

리전은 `asia-northeast3`(서울). OAuth 클라이언트는 다른 계정의 프로젝트에 있어도 된다. 그때 Calendar API 사용 설정·리디렉션 URI·테스트 사용자는 **OAuth 클라이언트가 있는 프로젝트**에서 관리한다.

1. 프로젝트에 결제 계정을 연결하고 예산 알림을 건다.
2. API 사용 설정: `run`, `sqladmin`, `artifactregistry`, `secretmanager`, `servicenetworking`, `compute`(모두 `.googleapis.com`).
3. Cloud SQL 비공개 IP용 연결: `gcloud compute addresses create google-managed-services-default --global --purpose=VPC_PEERING --prefix-length=16 --network=default` → `gcloud services vpc-peerings connect --service=servicenetworking.googleapis.com --ranges=google-managed-services-default --network=default`.
4. Cloud SQL: `gcloud sql instances create comedown-db --database-version=MYSQL_8_4 --edition=ENTERPRISE --tier=db-g1-small --region=asia-northeast3 --network=default --no-assign-ip --storage-size=10GB`, DB `comedown`(`utf8mb4`/`utf8mb4_0900_ai_ci`), 사용자 `comedown`(콘솔에서 만든다). 비공개 IP를 `-DbHost`로 쓴다.
5. Secret Manager(콘솔에서 만든다. PowerShell 파이프는 줄바꿈을 붙일 수 있다): `db-password`, `google-client-secret`, `comedown-token-key`(운영용으로 새로 만든 `openssl rand -base64 32`), 선택 `openai-api-key`.
6. 서비스 계정 `comedown-run`을 만들고 `roles/secretmanager.secretAccessor`를 준다.
7. Artifact Registry Docker 저장소 `comedown`(`asia-northeast3`).
8. OAuth 클라이언트에 리디렉션 URI 두 개(`https://comedown-<프로젝트번호>.asia-northeast3.run.app/login/oauth2/code/google`, `…/google-calendar`)와 시연 계정(테스트 사용자)을 넣는다. 주소는 첫 배포 뒤 스크립트가 출력한 값과 같은지 확인한다.

### 7.3 배포

로컬 Docker와 `gcloud auth login`이 필요하다. 저장소 루트에서:

```powershell
.\scripts\deploy-cloudrun.ps1 -ProjectId <프로젝트 ID> -DbHost <Cloud SQL 비공개 IP> -GoogleClientId <클라이언트 ID>
```

- `-FrontendDist <프론트 dist 경로>`: 프론트 빌드 결과를 ingress 이미지에 넣는다(없으면 확인용 화면). 프론트는 API를 상대 경로(`/api/...`)로 부르고 로그인은 `/oauth2/authorization/google`로 보낸다.
- `-WithOpenAi`: `openai-api-key` 비밀값을 연결한다(없으면 AI 문구는 대체 문구). `-OpenAiModel`로 모델을 바꾼다.
- `-RenderOnly`: 채운 서비스 정의만 출력한다. `-SkipBuild`: 이미 올린 같은 `-Tag` 이미지로 다시 배포한다.
- 배포 뒤 5절 순서로 확인하고, 로그는 `gcloud run services logs read comedown --region asia-northeast3`로 본다.
- **주소는 `https://comedown-<프로젝트번호>.asia-northeast3.run.app` 하나만 쓴다.** Cloud Run은 같은 서비스를 `https://comedown-<무작위>-du.a.run.app`로도 열어 두는데, 서버가 구글 리디렉션 주소를 브라우저가 들어온 주소로 만들기 때문에 그 주소로 들어가면 등록하지 않은 리디렉션 주소가 되어 로그인이 막힌다. 스크립트는 앞 주소를 출력한다.
- 행사가 끝나면 최소 인스턴스를 0으로 내리거나 서비스를 지우고 Cloud SQL 인스턴스를 중지한다.

### 7.4 자동 배포(CD, GitHub Actions)

`.github/workflows/deploy.yml`이 7.3과 같은 스크립트를 GitHub에서 실행한다.

| 언제 | 무엇을 |
|---|---|
| main에 merge → CI(빌드·테스트·문서 동기화) 성공 | CI가 검사한 그 커밋을 자동 배포 |
| Actions → CD → Run workflow(main) | 지금 main을 배포. 프론트만 바뀌었을 때 쓴다 |
| PR, 포크의 CI, 실패·취소된 CI, main이 아닌 브랜치 | 배포하지 않음 |
| 저장소 변수 `GCP_PROJECT_ID`가 없을 때 | 건너뜀(아래 준비 전) |

- 프론트는 공식 프론트 저장소 main을 받아 빌드한다. 프론트 앱(Expo)은 그 저장소의 `mobile/` 아래에 있으며, 저장소 맨 위 → `mobile/` 순서로 `package.json`을 찾는다. 둘 다 없으면 확인용 화면으로 배포한다.
  - 순서: `npm ci`(lock 파일이 없으면 `npm install`) → `build` 스크립트가 있으면 `npm run build`, 없으면 Expo 웹 빌드 `npx expo export --platform web --output-dir dist` → `dist`를 ingress에 넣는다.
  - 목업 모드: 프론트 `src/api/client.js`의 `const USE_MOCK = true;`(화면 미리보기용 가짜 응답)는 이 배포 빌드에서만 `false`로 바꾼다. 프론트 저장소 파일은 바꾸지 않는다. 바꾼 뒤에도 `USE_MOCK = true`가 남아 있으면 목업 화면을 배포하지 않도록 실패한다.
  - 프론트 저장소에 push해도 자동으로 돌지 않으니 프론트만 바뀌었으면 Run workflow로 배포한다.
- 로컬에서 같은 프론트 빌드를 만들려면 프론트 저장소의 `mobile/`에서 `USE_MOCK`을 `false`로 바꾼 뒤 `npm ci` → `npx expo export --platform web --output-dir dist`를 실행하고 7.3의 `-FrontendDist <mobile/dist 경로>`로 넘긴다.
- GCP 인증은 키 파일 없이 Workload Identity 연동(GitHub이 발급한 토큰을 GCP가 확인)으로 한다. 이 저장소의 main에서 돈 워크플로만 배포용 서비스 계정을 쓸 수 있다.
- 배포가 끝나면 `GET /api/auth/csrf`가 204인지 확인하고, 주소를 실행 요약에 남긴다. 한 번에 하나씩 배포하며, 기다리는 배포는 가장 최근 것만 남는다.

**GCP 준비(한 번만, 배포 프로젝트 계정으로).** `<P>` = 프로젝트 ID, `<N>` = 프로젝트 번호.

1. API: `gcloud services enable iamcredentials.googleapis.com sts.googleapis.com`
2. 배포용 서비스 계정: `gcloud iam service-accounts create github-deployer --display-name="GitHub Actions deployer"`
3. 권한(프로젝트): `roles/run.admin`(배포·공개 호출 권한), `roles/artifactregistry.writer`(이미지 push), `roles/browser`(프로젝트 번호 조회), `roles/compute.networkUser`(Direct VPC egress)를 각각 `gcloud projects add-iam-policy-binding <P> --member=serviceAccount:github-deployer@<P>.iam.gserviceaccount.com --role=<역할> --condition=None`으로 준다.
4. 실행용 계정을 쓸 권한: `gcloud iam service-accounts add-iam-policy-binding comedown-run@<P>.iam.gserviceaccount.com --member=serviceAccount:github-deployer@<P>.iam.gserviceaccount.com --role=roles/iam.serviceAccountUser`
5. Workload Identity 풀·공급자:
   - `gcloud iam workload-identity-pools create github --location=global --display-name="GitHub Actions"`
   - `gcloud iam workload-identity-pools providers create-oidc come-down-be --location=global --workload-identity-pool=github --issuer-uri=https://token.actions.githubusercontent.com --attribute-mapping="google.subject=assertion.sub,attribute.repository=assertion.repository,attribute.ref=assertion.ref" --attribute-condition="assertion.repository=='2026Ganzi-Thon/2026_GANZITHON_TEAM_12_BE' && assertion.ref=='refs/heads/main'"`
6. 이 저장소만 배포 계정을 쓰게 연결: `gcloud iam service-accounts add-iam-policy-binding github-deployer@<P>.iam.gserviceaccount.com --role=roles/iam.workloadIdentityUser --member="principalSet://iam.googleapis.com/projects/<N>/locations/global/workloadIdentityPools/github/attribute.repository/2026Ganzi-Thon/2026_GANZITHON_TEAM_12_BE"`

**GitHub 준비(저장소 Settings → Secrets and variables → Actions → Variables, 저장소 관리자 권한 필요).** 비밀값이 아니라 변수다. 비밀값은 GCP Secret Manager에만 있다.

| 변수 | 값 |
|---|---|
| `GCP_PROJECT_ID` | 프로젝트 ID |
| `GCP_WORKLOAD_IDENTITY_PROVIDER` | `projects/<N>/locations/global/workloadIdentityPools/github/providers/come-down-be` |
| `GCP_DEPLOY_SERVICE_ACCOUNT` | `github-deployer@<P>.iam.gserviceaccount.com` |
| `CLOUD_SQL_PRIVATE_IP` | Cloud SQL 비공개 IP |
| `GOOGLE_CLIENT_ID` | 운영 OAuth 클라이언트 ID |
| `DEPLOY_WITH_OPENAI` | `true`면 `openai-api-key` 비밀값을 연결(선택) |

준비가 끝나면 Actions → CD → Run workflow로 한 번 돌려 확인한다.

## 확인한 범위

- 2026-11-17 로컬에서 `docker build`로 이미지를 만들고(약 576MB), 컨테이너를 로컬 MySQL에 붙여 프로필 없이 실행했다. `SERVER_FORWARD_HEADERS_STRATEGY=framework`와 `X-Forwarded-Proto: https`·`X-Forwarded-Host` 헤더를 넣었을 때 `XSRF-TOKEN` 쿠키에 `Secure`가 붙고, 구글 리디렉션 주소가 `https://<전달받은 호스트>/login/oauth2/code/google`과 `…/google-calendar`로 만들어졌다. `POST /api/dev/login`은 CSRF 토큰을 넣어도 401이고 세션이 생기지 않았다(local 전용 기능 없음). 컨테이너는 root가 아닌 계정으로 실행된다.
- 2026-11-17 Cloud Run 구성을 로컬 Docker로 흉내 냈다: 임시 MySQL 8.4 + backend(8081) + ingress(nginx)를 같은 네트워크 네임스페이스에 띄우고 `run.app` 형태의 `Host`와 `X-Forwarded-Proto: https`를 넣었다. `/`와 없는 경로는 프론트 `index.html`, `/assets/*`는 1년 캐시, `GET /api/auth/csrf` 204 + `Secure` 쿠키, 구글 리디렉션 주소 두 개가 `https://<run.app 호스트>/login/oauth2/code/google`·`…/google-calendar`, 클라이언트가 보낸 `Forwarded: host=…`·`X-Forwarded-Prefix`는 무시, `/api/me` 401, `POST /api/dev/login` 401, 2MB 본문은 nginx를 통과(413 아님)했다. `--build-context site=<dist>`가 확인용 화면을 프론트 빌드로 바꾸는 것도 확인했다. `deploy-cloudrun.ps1 -RenderOnly`로 서비스 정의가 빈 자리 없이 채워지는 것을 확인했다.
- 2026-11-17 GCP에 처음 배포했다(`deploy-cloudrun.ps1`, 서울, Cloud SQL `db-g1-small` 비공개 IP). 서비스 정의가 그대로 받아들여졌고(인스턴스 1개, CPU 항상 할당), backend가 Direct VPC로 Cloud SQL에 붙어 Flyway가 migration 5개를 적용한 뒤 약 14초 만에 떴다. 운영 주소에서 `/` 확인용 화면 200, `GET /api/auth/csrf` 204 + `Secure` 쿠키, 구글 리디렉션 주소 두 개가 `https://comedown-<프로젝트번호>.asia-northeast3.run.app/login/oauth2/code/…`, `/api/me`·`/api/cbi/questions` 401, `POST /api/dev/login` 401이었다. 즉 Cloud Run 앞단이 `X-Forwarded-Proto: https`를 붙이고 nginx가 그대로 넘긴다.
- 처음 실행에서 Windows PowerShell 5.1이 gcloud의 진행 메시지(stderr)를 종료 오류로 바꿔 스크립트가 멈췄다. 외부 명령은 종료 코드로만 성공을 판단하도록 고쳤다.
