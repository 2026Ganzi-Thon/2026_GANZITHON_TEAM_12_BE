# Come-down 계산 정책 (v1, 2026-11-12)

출처: 팀장 "백엔드 설계 수정 요청 1"(2026-11-12). 명세 v0.2에서 `POLICY_PENDING`으로 남겼던 산식의 확정 값입니다.
**모든 수치는 초기값**입니다. 결과 행에 `calculation_version`(또는 `algorithm_version`)을 남기고 실제 데이터를 보며 조정합니다. 버전을 올리면 해당 파생 데이터를 다시 계산합니다.

각 절의 **구현 해석**은 문서에 명시되지 않아 백엔드가 임시로 정한 해석입니다. 확인 필요 목록은 [검토 결과](검토결과.md) 마지막 절에 있습니다.

| 절 | 정책 | 버전 | 담당 |
|---|---|---|---|
| 1 | 일정 부하·위험 주차 | `load-v1` | 일정축 (schedule) |
| 2 | CBI 채점 | `cbi-ko-2026.11.2` | HRV축 (cbi) |
| 3 | 카메라 HRV 측정 계산·품질 | `hrv-cam-v1` | HRV축 (checkin) |

| 6 | 내 범위 중 현재 위치 | `recovery-v1` / `load-v1` | HRV축 (experience.reports) |

## 1. 일정 부하 (`load-v1`)

### 집계 대상
- 포함: 일 관련 카테고리(`CLASS` `ASSIGNMENT` `EXAM` `PRESENTATION` `PART_TIME` `CLUB` `WORK_MEETING` `STUDY`)와 `OTHER`. 분류가 끝나지 않은 일정은 가중치 1.0으로 포함(AI 실패 시 규칙 분류가 있어 드묾).
- 제외: 개인 카테고리(`EXERCISE` `APPOINTMENT` `PERSONAL` `RECOVERY`), `created_by_app = true`, `transparency = transparent`(한가함), 취소된 일정.

### 주간 부하 점수
`load_score = Σ(일정 시간 × 가중치)`

| 조건 | 가중치 |
|---|---|
| 기본 | 1.0 |
| `EXAM`, `PRESENTATION` | × 1.5 |
| 22시~07시에 걸친 시간, 또는 토·일 시간 | × 1.5 |

- 두 조건이 겹치면 곱합니다(최대 2.25). 시간대 가중은 해당하는 구간만 나눠서 적용합니다.
- 겹친 일정: 같은 시간대는 한 번만 셉니다. 겹친 구간에는 높은 가중치를 적용합니다.
- 종일 일정: 시간에 넣지 않습니다. `isDeadline`이거나 `EXAM`·`PRESENTATION`이면 `deadline_count`에만 더합니다.

### 지표
| 지표 | 정의 |
|---|---|
| vs_usual_pct | (이번 주 부하 점수 ÷ 직전 4주 평균 − 1) × 100. 직전 4주 평균이 0이면 null + `ZERO_BASELINE`, 직전 데이터가 2주 미만이면 null + `INSUFFICIENT_DATA` (`vs_usual_unavailable_reason`에 저장) |
| rest_days | 집계 대상 일정이 하나도 없는 날 수 |
| late_night_count | 22시 이후 끝나거나 07시 이전에 시작하는 집계 대상 일정 수 |
| deadline_count | `isDeadline = true`이거나 `EXAM`·`PRESENTATION`인 일정 수 |
| 연속 일정일 | 집계 대상 일정이 있는 날이 끊기지 않고 이어진 최대 일수(주 경계를 넘어 계산) |

### 위험 주차 (`risk_level`)
조건 점수를 더해 판정합니다(v0.2의 "WATCH = 조건 1개" 정의를 대체).

| 조건 | 점수 | risk_reasons |
|---|---|---|
| 부하 +30% 이상 (+15% 이상이면 1점) | 2 | `LOAD_HIGH` |
| 마감 3개 이상 (2개면 1점) | 2 | `DEADLINES` |
| 쉬는 날 0일 | 1 | `NO_REST_DAY` |
| 심야 일정 3회 이상 | 1 | `LATE_NIGHT` |
| 연속 일정일 10일 이상 | 1 | `LONG_STREAK` |

0~1점 `NONE` / 2~3점 `WATCH` / 4점 이상 `RISK`. 앞으로의 주는 일정이 덜 채워져 부하가 낮게 나오므로 동기화할 때마다 다시 계산합니다.

**구현 해석(확인 필요)**
- `vs_usual_pct`가 null이면 `LOAD_HIGH` 점수는 0점입니다.
- `risk_reasons`에는 1점 이상 받은 조건을 모두 넣습니다(부분 점수 1점 포함).
- `total_hours`는 겹친 시간을 한 번만 센 집계 대상 일정 시간 합(가중치 미적용)입니다.
- "22시~07시", "토·일"은 서울 시간 기준이며 사용자 수면 설정(`sleep_start/end`)과 무관한 고정 구간입니다.

## 2. CBI 채점 (`cbi-ko-2026.11.2`)

| 척도 | 보기 (option 0 → 4) | 점수 |
|---|---|---|
| FREQUENCY | 항상 / 자주 / 가끔 / 드물게 / 전혀 또는 거의 없음 | 100 / 75 / 50 / 25 / 0 |
| DEGREE | 매우 많이 / 많이 / 어느 정도 / 조금 / 거의 없음 | 100 / 75 / 50 / 25 / 0 |

- 문항 13개(빈도형 10, 정도형 3: 7·8·9번). 문항 문구는 [API.md](API.md) 2절 표. 13번은 역채점(점수 = 100 − 환산값).
- 하위척도 점수 = 응답 점수 평균(0~100): `PERSONAL` 1~6번, `WORK` 7~13번. 어느 하나 75 이상이면 `high_risk`.
- 화면은 문항 순서를 섞어서 보여주고(원 매뉴얼 권고), 서버의 `no`는 고정합니다.
- `cbi_answers.answer_option`은 원래 선택(0~4), `answer_value`는 역채점까지 반영한 점수입니다.

## 3. 카메라 HRV 측정 (`hrv-cam-v1`)

참고 구현: `com.comedown.checkin.domain.measurement.HrvAnalyzer` (팀장 전달). 입력은 프레임 타임스탬프 `t`(ms, 시작 = 0)와 프레임별 빨강·초록 평균 밝기 `r`, `g`.

1. 앞 10초 제거. 분석 구간 50초 미만이면 `TOO_SHORT`, 초당 20프레임 미만이면 `LOW_FPS`.
2. 30Hz 균일 간격으로 보간.
3. 밝기 반전 + 0.7~3.5Hz 대역 통과 필터(양방향).
4. 자기상관으로 심박 주기 추정(10초 구간별 중앙값). 반복성 0.5 미만이면 `NO_PULSE`.
5. 박동 꼭짓점 검출(최소 간격 = max(0.33초, 주기 × 0.6)) + 포물선 보간. 박동 3개 미만이면 `NO_PULSE`.
6. 박동 간격 계산 후 이상 간격 제거: 333~1500ms 범위, 주변 5개 중앙값과 20% 이내, 평균 박동 모양과 상관 0.9 이상.
7. 연속으로 유효한 간격 쌍만으로 RMSSD 계산.
8. R·G 채널 각각 계산 후 채택. 참고 구현은 **성공한 채널을 우선**하고, 둘 다 성공하거나 둘 다 실패하면 잡음비가 낮은 쪽을 채택합니다.

| 등급 | 조건 |
|---|---|
| `RETRY` (`TOO_NOISY`) | 유효 간격 쌍 30개 미만, 또는 유효 비율 70% 미만, 또는 잡음비 0.12 초과 |
| `GOOD` | 유효 비율 90% 이상 + 잡음비 0.06 이하 |
| `FAIR` | 그 외 |

- 잡음비 = 6Hz 이상 고주파 성분의 크기(MAD 기반) ÷ 박동 진폭(5~95 백분위 차). 테스트 버전 검증에서 잡음이 큰 측정이 품질을 통과해 RMSSD 오차가 30~260%까지 난 사례가 있어 필수 조건입니다.
- 저장: `valid_beats`/`rejected_beats` = 유효/제외된 박동 **간격** 수, `noise_ratio`, `channel`, `frame_count`·`duration_sec`·`fps`(앞 10초 제거 후 분석 구간 기준), `algorithm_version = hrv-cam-v1`. 원신호는 저장하지 않습니다.
- MANUAL 입력은 계산하지 않고 `UNVERIFIED`로 저장합니다(`algorithm_version = manual-v1`).

## 4. 하루 대표값·기준선·회복 상태 (`recovery-v1`)

모든 계산은 **ln(RMSSD)** 단위로 하고 화면 표시만 exp로 ms 변환합니다. 단순 RMSSD 산술 평균은 사용하지 않습니다.

| 항목 | 정의 |
|---|---|
| 하루 대표값 | 그날 **첫 번째 적격 측정**(GOOD·FAIR)의 ln 값. 첫 측정이 RETRY이고 재측정이 GOOD·FAIR면 그 재측정. 같은 날 나중 값(운동 후, 저녁 등)은 섞지 않음 |
| 적격일 | 대표값이 있고, 컨디션·교란 요인 입력이 완료됐고, 교란 요인(음주·아픔·카페인)이 없는 날 |
| 초기 기준선 | 첫 적격 7일의 평균·표준편차. "최근 7일 제외"는 초기 기준선에는 적용하지 않음 |
| 기준선 갱신 | 지수 이동 평균, 반감기 14일 (α = 1 − 0.5^(1/14) ≈ 0.0483) |
| 갱신에 쓰는 값 | 8일 이전(최근 7일 제외) 적격일 값만, 하루 1번 |
| 이상치 제외 | 현재 기준선에서 2.5 표준편차 이상 벗어난 값은 갱신에 쓰지 않음 |
| 갱신 정지 | 회복 상태가 LOW인 동안 기준선 갱신 정지(`baseline_frozen = true`) |
| 평균 갱신 | 평균 ← 평균 + α × (값 − 평균) |
| 분산 갱신 | 분산 ← (1 − α) × (분산 + α × (값 − 평균)²) (평균 갱신 전의 평균 사용) |
| 표준편차 최소값 | 0.05 (ln 단위). 초기 며칠 값이 비슷해 범위가 지나치게 좁아지는 것 방지(제안값) |
| 7일 추세 (`trend_ln`) | 최근 7일 안의 대표값 평균. 대표값 3개 미만이면 `INSUFFICIENT` |
| 정상 범위 | 기준선 평균 ± 1 표준편차 |
| LOW | 7일 추세 < 평균 − 1SD, 또는 최근 대표값 3개 연속 < 평균 − 1SD |
| NORMAL | 위에 해당하지 않음 |
| change_pct | (exp(추세 − 기준선 평균) − 1) × 100 |

- 교란일(음주·아픔·카페인)은 기준선뿐 아니라 7일 추세와 3개 연속 판정에서도 제외합니다. 그래프에는 회색으로 표시합니다.
- 상태 순서: 초기 기준선 전 `BUILDING` → 추세 대표값 3개 미만 `INSUFFICIENT` → `LOW` / `NORMAL`.
- 7일차(기준선 확정 당일): 기준선과 7일 추세가 같은 데이터라 change_pct ≈ 0, `NORMAL`이 정상입니다.
- 0~100 회복 점수는 사용하지 않습니다. 화면은 "평소 대비 %" + 상태로 표시합니다.

**구현 해석(확인 필요)**
- 초기 기준선 표준편차는 표본 표준편차(n − 1)로 계산합니다.
- 갱신 정지 중 "8일 이전"이 된 값은 갱신에 쓰지 않고 버립니다(정지 해제 후 소급 반영하지 않음).
- "최근 대표값 3개 연속"은 측정하지 않은 날·교란일을 건너뛴 최근 대표값 3개입니다.
- "최근 7일"은 계산 대상 날짜를 포함한 7일(D−6 ~ D)입니다.
- 갱신 시점: 날짜 D를 계산할 때 적격일 D−7의 값을 한 번 반영합니다(각 적격일은 7일 뒤 한 번). 초기 기준선에 쓴 7일은 다시 반영하지 않습니다. 측정 없는 날에도 차례는 지나갑니다.
- 갱신 정지 판단: **전날**(측정 없는 날도 내부적으로 판정)의 상태가 LOW면 D의 갱신을 건너뜁니다. 그날 행의 `baseline_frozen = true`입니다.
- 표준편차 최소값 0.05는 사용할 때(이상치·정상 범위·LOW 판정·저장값) 적용하고, 내부 분산은 산식대로 갱신합니다.
- 이상치: |값 − 평균| ≥ 2.5 × SD면 갱신에 쓰지 않습니다.
- 7일 추세·3개 연속 판정은 **적격일** 값만 씁니다. 교란일뿐 아니라 컨디션을 입력하지 않은 날도 "무교란으로 간주하지 않음"([API.md](API.md) 6절)에 따라 제외합니다. 두 판정 모두 그날의 기준선(평균 − 1SD)과 비교합니다.
- `trend_ln`은 기준선 확정 전에도 계산해 저장하고, `change_pct`는 기준선이 있을 때만 계산합니다(소수 첫째 자리 반올림, HALF_UP).
- 기준선은 지수 이동 평균이라 과거 값이 바뀌면 이후가 모두 달라지므로, 재계산은 첫 기록부터 다시 재생합니다(참고 구현 `com.comedown.recovery.domain.policy.RecoveryCalculator`).

## 5. 2주 연속 낮음 (`LOW_RECOVERY_2W`)

- 정의: 최근 14일 중 대표값이 있는 날이 7일 이상이고, 그 날들의 `recovery_status`가 모두 `LOW`.
- 측정하지 않은 날은 판정에서 빠집니다(낮음으로도, 정상으로도 세지 않음).
- 닫은 뒤 재노출: 조건이 해제됐다가(`resolved_at`) 다시 충족되면 새 안내로 노출합니다. 같은 연속 구간에서는 다시 띄우지 않습니다.
- `CBI_HIGH`(어느 하위척도든 75 이상)는 기존과 같습니다.

**구현 해석(확인 필요)**
- 교란일도 대표값이 있으면 "대표값이 있는 날"에 포함합니다(그날의 `recovery_status`는 추세 기준으로 계산됨).

## 6. 내 범위 중 현재 위치

| 항목 | 정의 |
|---|---|
| 공개 조건 | 28일차 이후, 7일 추세 값이 20개 이상 |
| 최저·최고 | 지금까지의 7일 추세 값(회복은 ln, 부하는 주간 부하 점수)의 하위 5%, 상위 5% 백분위 |
| 위치 | (현재 − 최저) ÷ (최고 − 최저) × 100, 0~100으로 제한 |
| 최저 = 최고 | null + `INSUFFICIENT_DATA` |

- 회복과 일정 부하는 따로 계산합니다.

**구현 해석(확인 필요)**
- 백분위는 선형 보간 방식(HrvAnalyzer의 `percentile`과 같음)을 씁니다.
- 부하는 주 단위 값(주간 부하 점수)을 그대로 씁니다(팀장 답변: HRV는 하루, 부하는 주 단위). 부하에도 "20개 이상"을 적용하면 약 20주 뒤에 공개되므로, 부하의 최소 표본 수는 확인이 필요합니다. 확정 전에는 20개 기준을 유지하고 미달이면 `load: null` + `INSUFFICIENT_DATA`입니다.

### 회복 리포트 그래프
HRV(하루 단위)와 일정 부하(주 단위)는 X축(날짜)만 공유하고 표현을 다르게 합니다. HRV는 날마다 점(교란일 회색) + 7일 평균선 + 날짜별 정상 범위 띠, 일정 부하는 해당 주 월~일 폭의 막대입니다. 응답 형식은 [API.md](API.md) 7절.
