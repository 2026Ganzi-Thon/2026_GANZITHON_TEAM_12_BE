# Come-down(캄다운) 백엔드 구조 설계

설계일: 2026-11-12 · 제안 v1.0 · 범위: 독립 백엔드 저장소

## 1. 설계 출발점

기준은 [서비스 요구사항](서비스_요구사항.md), [API 명세](API.md), [ERD](ERD.md), [IA 차트](IA_초안.png)다. 기존 Java 소스의 패키지·클래스·구현 상태를 설계 근거로 사용하지 않았다. 아래 디렉터리는 **새로 개발할 목표 구조**이며, 실제 소스를 이 구조로 이동한 결과가 아니다.

Come-down의 핵심은 **캘린더 연결 → 일정 부하 파악 → 아침 체크 → 개인 기준선과 회복 판단 → 빈 시간의 회복/대비 행동 추천 → 승인 시 캘린더 반영**이다. 가입 시 CBI, 초기 적격 측정 7일, 28일차 비교, 안전 안내가 이 흐름에 연결된다.

**단일 Spring Boot 애플리케이션·단일 Gradle 프로젝트·단일 MySQL**로 시작한다. 기능별 패키지에 데이터와 규칙을 모으는 모듈형 모놀리스다. 두 개발자가 기능 단위로 나눠 작업할 수 있도록 하되 마이크로서비스·다중 Gradle 모듈·메시지 브로커를 선행 도입하지 않는다.

## 3. 기능 패키지 안의 규칙

직접 HTTP API가 있는 기능의 예시다. 파일명은 설계 예시이며 기존 클래스 재사용 지시가 아니다.

```text
recommendation/
├── api/
│   ├── SuggestionQueryController.java
│   └── dto/
├── contract/                              # 다른 기능에 공개할 요청/결과 record·서비스
│   ├── SuggestionQuery.java
│   └── SuggestionCommands.java
├── application/
│   ├── SuggestionCommandService.java
│   ├── SuggestionQueryService.java
│   └── port/                              # 외부 자원이 필요한 기능에만 추가
├── domain/
│   ├── Suggestion.java
│   ├── SuggestionStatus.java
│   └── policy/
│       ├── RecoverySuggestionPolicy.java
│       └── PrepareAheadPolicy.java
└── infrastructure/
    └── persistence/
        ├── SuggestionJpaRepository.java
        └── SuggestionQueryRepository.java
```

| 위치 | 책임 | 두지 않을 것 |
|---|---|---|
| api | HTTP 바인딩·검증·응답 변환 | 점수 계산·Repository 직접 호출 |
| contract | 기능 간 공개 서비스 계약과 불변 데이터 | JPA Entity·프록시·토큰 원문 |
| application | 소유 데이터의 유스케이스·트랜잭션 | 다른 기능의 테이블 직접 갱신 |
| domain / policy | 엔티티·상태 전이·계산 규칙 | Controller·HTTP/외부 SDK 호출 |
| infrastructure / persistence | 해당 기능의 JPA·쿼리 | 다른 기능 소유 테이블의 쓰기 우회 |
| application / port | Google·AI처럼 필요한 외부 기능의 좁은 인터페이스 | 모든 메서드를 담는 범용 거대 인터페이스 |

단순 CRUD의 Repository는 JPA 인터페이스 하나로 충분하다. 모든 저장소에 인터페이스+어댑터+도메인 모델+JPA Entity를 중복 생성하지 않는다. JPA Entity를 domain에 둘 수 있지만 외부 계약으로 노출하지 않는다. 다른 기능의 id는 값으로 보관하고 기능 간 Entity 연관관계로 내부를 연결하지 않는다. DB FK는 ERD에 맞게 유지한다.

`checkin`, `recovery`, `schedule`처럼 복합 응답의 내부 계산·저장을 담당하는 기능은 HTTP Controller가 없어도 된다. 브라우저에 결과를 묶어 내려주는 책임은 `experience`에 둔다.

## 4. 기능별 데이터와 규칙 책임

| 기능 | 책임 | 쓰기 소유 테이블 |
|---|---|---|
| account | 회원·닉네임·생활 정보·동의 이력·Google 자격정보·온보딩 진행 상태 저장 | users, user_consents, user_settings, user_preferred_activities, oauth_tokens |
| cbi | 버전별 13문항·역문항·채점·INITIAL/DAY28 회차 | cbi_assessments, cbi_answers |
| calendar | Google 일정·직접 수정 규칙·분류·빈 시간·앱 일정 생성/삭제 | calendar_events, event_category_overrides |
| schedule | 지난달/주간 부하·마감 몰림·위험한 주 계산 | weekly_loads |
| checkin | 하루 체크·재측정·호흡 완료·컨디션·품질 판정 | morning_checks, hrv_measurements |
| recovery | 적격 측정일·기준선·추세·회복·정상 범위·내 범위 계산 | hrv_daily_states |
| recommendation | 제안 생성·승인/거절/만료/되돌림·수행 이력 | suggestions |
| safety | CBI/회복 결과에 따른 안내 판단·확인/해제 | safety_alerts |
| subscription | 28일 체험·FREE/TRIAL/PREMIUM 자격. 결제 연동은 별도 범위 | subscriptions |
| ai | 해석 문구 캐시·생성/대체 여부·입력 hash·모델 메타데이터 | ai_outputs |
| shared.idempotency | 사용자·작업·키 기준 재시도 결과 및 진행 상태 | api_idempotency_keys |
| experience | 온보딩·홈·아침 결과·캘린더 갱신·리포트·탈퇴 흐름 조합 | 없음 |
| integration | Google/OpenAI 요청 전송·타임아웃·응답 형식 처리 | 없음 |

ERD의 **18개 테이블에 각각 쓰기 소유자가 하나씩** 존재한다. `subscriptions`가 있어도 현재 API에는 결제 엔드포인트가 없으므로 결제 Controller를 임의로 추가하지 않는다. 용어 사전은 IA/명세대로 정적 콘텐츠이며 테이블/API를 새로 만들지 않는다. Spring Session 테이블은 shared.security의 기술 저장소이며 도메인 테이블 18개에 포함하지 않는다.

ai_outputs는 공통 AI 결과 전부를 저장하는 만능 테이블이 아니다. 일정 분류는 calendar_events, 추천 카드 문구는 suggestions의 소유자가 저장한다. ai는 그 외 리포트/요약 문구 캐시를 소유한다.

## 5. 참조 방향과 순환 의존 방지

```text
HTTP
 ├─ 단일 기능 API ─────────→ 그 기능의 application
 └─ 복합 API → experience ─→ 각 기능의 contract → 각 기능 application

기능 application → 자기 domain/persistence
외부 기능이 필요한 application → 자신이 정의한 port
integration의 adapter → 그 port를 구현 + Google/OpenAI SDK
모든 기능 → 필요한 shared 기술 코드
```

- experience만 여러 기능을 조합한다. account↔cbi, calendar↔recommendation 같은 기능 간 양방향 호출을 만들지 않는다. feature→experience 의존도 금지한다.
- 기능 간 읽기/명령은 contract로 요청한다. Repository/Entity를 import하지 않는다. 홈·리포트도 테이블을 직접 join하는 새 Repository를 만들지 않고 기능별 읽기 계약의 스냅샷을 조합한다. 성능 근거가 생기면 명시적인 읽기 전용 projection을 별도 ADR로 추가한다.
- shared는 어느 비즈니스 기능에도 의존하지 않는다. 회복 산식·CBI 점수·일정 가중치·추천 기준을 shared/util에 넣지 않는다.
- integration은 전송 어댑터다. 일정 부하·추천·회복 정책을 갖지 않으며 비즈니스 application을 호출하지 않는다. 전송 어댑터가 계약의 port 타입을 참조하는 것은 허용한다.
- Google 자격정보는 account가 암호화 저장한다. experience가 account의 토큰 접근 경계를 거쳐 calendar 작업을 연결하며, 토큰은 로그/HTTP/일반 contract DTO에 넣지 않는다. 요청 수명 내 전용 credential handle을 포트에 전달하고 토큰 복호화는 제한된 어댑터 경계에서 수행한다. 공유 DTO로 토큰을 돌려주지 않는다.
- OAuth 등록·성공/실패 처리·자격정보 저장 어댑터는 account.infrastructure.security에 둔다. shared.security는 인증 주체/CSRF/세션 같은 공통 기술 타입과 필터만 제공한다. 필터 체인 조립 시 account의 핸들러를 프레임워크 인터페이스로 주입하고 shared가 account의 application을 import하게 만들지 않는다.
- 규칙 기반 분류/문구 대체는 calendar·recommendation·ai 등 해당 소유 기능의 정책이다. OpenAI 전송 어댑터에 제품 규칙을 넣지 않는다.

## 6. API 주소와 내부 패키지는 다르다

`/api/hrv/measurements`라는 주소가 있다는 이유로 전체 서비스를 hrv 패키지 아래에 넣지 않는다. 측정 기록은 checkin, 회복 계산은 recovery, 여러 결과를 돌려주는 저장 흐름은 experience.morning에 배치한다.

API 39개의 HTTP 책임과 테이블 18개의 소유권 전체 목록은 [책임 매핑](책임_매핑.md)에 둔다. OAuth 로그인/캘린더 권한 부여 경로와 local 전용 API도 별도로 표시한다. 같은 HTTP 경로에 기능 Controller와 experience Controller를 중복 등록하지 않는다.

## 7. 핵심 업무 흐름

### 가입·온보딩

experience.onboarding이 profile → CBI 또는 비동의 건너뛰기 → 생활 정보 → 캘린더 분석 → 완료를 제어한다. account가 users의 단계만 저장하고, CBI는 cbi가 저장한다. 완료 시 account의 완료일과 subscription의 체험 시작은 같은 DB 트랜잭션에서 반영한다. account가 cbi/recovery를 직접 호출하지 않는다.

### 캘린더 동기화·분류 수정

experience.calendarflow가 자격정보 확인 → Google 조회 → calendar 저장/분류 → schedule 재계산 → PRE_START 갱신을 조합한다. 외부 조회·AI 처리는 긴 DB 트랜잭션 밖에서 하고 저장/파생 갱신에 실패하면 결과를 정상이라고 반환하지 않는다. API의 200 완료 응답은 명세상 필요한 갱신까지 끝난 상태다. 나중에 202 작업 방식으로 바꾸려면 먼저 API 계약을 변경한다.

### 측정·컨디션 완료

experience.morning이 checkin 저장 → recovery 재계산 → schedule 읽기 → 추천 갱신 → safety 평가 → TodayResult 조합을 맡는다. 재측정/컨디션 변경은 해당 날짜 이후 파생 상태를 다시 계산한다. 체감 컨디션을 입력하기 전을 '교란 없음'으로 간주하지 않는다. 초기 7일·LOW 산식은 확정 정책 버전을 받은 뒤 구현한다.

### 추천 승인·되돌리기

experience.suggestions가 recommendation의 상태/등록 키 확보 → calendar 빈 시간 확인·외부 등록 → recommendation 확정을 조합한다. recommendation은 상태와 중복 키를 소유하며 calendar는 Google 쓰기를 소유한다. APPROVING 저장은 짧은 트랜잭션, Google 호출은 밖에서, 결과 확정은 새 트랜잭션이다. 타임아웃은 등록 키로 조회해 확인하며 바로 FAILED로 확정하지 않는다. 재시도 작업은 MVP에서 같은 애플리케이션의 scheduler로 시작할 수 있고 메시지 브로커는 필수가 아니다.

APPROVING으로 전환할 때 사용자별 경합 제어 안에서 다른 APPROVING/APPROVED 시간 예약도 검사해 다른 승인 요청이 같은 구간을 가져가지 않게 한다. 외부 호출 동안 긴 DB 트랜잭션을 유지하는 방식으로 해결하지 않는다. Google의 다른 앱이 동시에 일정을 추가하는 경합은 최신 빈 시간 재확인으로 줄일 수 있지만 완전히 차단할 수는 없다.

### 홈·리포트·안전 안내

experience.home/reports가 account·checkin·recovery·schedule·recommendation·cbi·subscription의 읽기 계약과 ai 해석을 조합한다. cbi/recovery는 safety를 호출하지 않고 해당 결과로 experience가 safety 평가 명령을 보낸다. 자료 부족·비동의·아직 28일 전인 상태는 명세의 null/잠금 사유로 반환한다. 범위 위치의 회복 값과 일정 부하 값은 각각 recovery와 schedule이 계산한다.

### 연결 해제·건강 기록 삭제·탈퇴

experience.accountlifecycle이 각 기능의 삭제 계약을 순서대로 호출한다. account가 전체 Repository를 가져와 일괄 삭제하지 않는다. 잠금/삭제 진행 상태로 새 입력을 막고 Google 정리 → 관련 참조 해제 → 파생 데이터·건강 응답 캐시 → 원본 데이터 → 세션/사용자 순서를 명세에 맞춰 조율한다. 캘린더만 해제하는 경우와 건강 기록만 삭제하는 경우, 탈퇴는 서로 다른 유스케이스다. 외부 정리 실패는 재시도하며 민감정보가 캐시에서 복원되지 않게 한다.

HRV축 기능의 건강 기록 삭제 계약(각 기능이 자기 테이블만 지운다):

| 기능 | 계약 | 지우는 것 |
|---|---|---|
| recommendation | `SuggestionDataDeletion.removeHealthBasis` | 미승인 RECOVERY 제안 삭제, 남는 제안의 판단·회복 사유·문구 제거 |
| safety | `SafetyDataDeletion.deleteAll` | safety_alerts |
| cbi | `CbiDataDeletion.deleteAll` | cbi_assessments(+ cbi_answers CASCADE) |
| recovery | `RecoveryDataDeletion.deleteAll` | hrv_daily_states(기준선·추세·카운터) |
| checkin | `CheckinDataDeletion.eraseHealthData` | hrv_measurements, morning_checks 건강 필드·completed_at(호흡 기록 없는 체크는 행 삭제) |
| shared.idempotency | `IdempotencyService.deleteForUser(userId, "hrv-" / "cbi-")` | 측정·CBI 재시도 응답 캐시 |

건강 기록 삭제는 위 순서로 한 트랜잭션에서 호출한다(외부 호출 없음). 탈퇴는 users 삭제의 FK CASCADE가 이 테이블들을 함께 지우므로 별도 호출이 필요 없다(suggestions의 일정 참조 해제 순서는 calendar 쪽에서 조율).

## 8. 두 개발자의 작업 경계

2026-11-12 팀 합의로 확정한 분담이다. **HRV축(신체)** 과 **일정축(Google 캘린더 연동)** 으로 나눈다. 패키지 구조·HTTP 책임·테이블 소유권([책임 매핑](책임_매핑.md))은 바뀌지 않으며, 아래는 각 패키지·파일을 누가 주로 작성하고 리뷰하는지에 대한 분담이다.

| 담당 | 기능 패키지 | experience 흐름 | 상대에게 제공할 계약 |
|---|---|---|---|
| **HRV축** | cbi, checkin, recovery, safety, recommendation(제안 상태·조회·건너뛰기·했어요, RecoverySuggestionPolicy) | assessments, morning, home, reports(`/api/reports/recovery`, `/api/reports/four-week`) | CBI 결과·회복 스냅샷·제안 상태 전이(생성/APPROVING/APPROVED/FAILED/되돌림)·안전 평가 |
| **일정축** | account, calendar, schedule, subscription, recommendation.domain.policy.PrepareAheadPolicy(PRE_START 규칙) | onboarding, calendarflow, accountlifecycle, suggestions(생성·다른 시간·승인·되돌리기), reports(`/api/schedule/report`) | 동의·측정 켜짐·온보딩 상태, 주간 부하 스냅샷, 빈 시간 조회, 캘린더 일정 등록/삭제, Google 자격정보 handle |
| **공통 (편집 담당: HRV축)** | shared(config·security·error·time·idempotency), DB 마이그레이션, build.gradle·CI, local 전용 개발 API | — | 오류 형식·현재 사용자·시간·재시도 키·테스트 지원 |

- **integration.google**은 일정축이 작성한다. **ai·integration.openai**는 핵심 기능 완성 후 AI 도입 단계에서 담당을 정한다. 그 전까지 문구는 각 소유 기능의 규칙 기반 문구(`fallback: true`)로 내려준다.
- **PRE_START 규칙**은 일정축이 작성하지만 파일 위치는 `recommendation/domain/policy/`다. 제안 저장·상태 전이는 recommendation의 계약을 통해서만 한다.
- **제안 승인 흐름**(experience.suggestions)은 일정축이 Google 등록·타임아웃 재확인·재시도를 조합하고, recommendation의 상태 전이 계약(HRV축)을 호출한다. 상태 전이 계약은 승인 흐름 구현 전에 인터페이스 PR로 먼저 합의한다.
- **홈**(experience.home)은 HRV축이 조합하고 일정축은 주간 부하·PRE_START 제안 읽기 계약을 제공한다.
- 공통 영역은 HRV축이 편집하고 일정축이 리뷰한다. 일정축이 공통 코드를 바꿔야 하면 이슈로 요청하거나 같은 PR에서 리뷰를 받는다. OAuth 로그인 설정은 `SecurityFilterChainContributor`로 account(일정축)에서 덧붙이므로 shared.security 파일을 동시에 고치지 않는다.
- Google 로그인 완성 전에도 HRV축이 로컬에서 API를 시험할 수 있도록 local 전용 테스트 로그인을 공통 작업으로 둔다.
- local 전용 시계 이동(`shared.time.AdjustableClock`)과 시연 시드(`experience.devseed`)도 공통 작업으로 HRV축이 작성한다. 시드는 각 기능 contract로만 기록을 넣고, 계정 상태는 account의 local 전용 `DemoAccountSetup` 계약(일정축 리뷰)으로 준비한다. 일정 시드(캘린더 일정·주간 부하)는 schedule·calendar 쓰기 계약이 생기면 그 계약으로 추가한다.

## 9. 구현 순서와 미확정 사항

1. API/ERD 책임 매핑·오류/인증 사용자/시계·외부 포트 계약을 합의하고 신규 프로젝트 골격을 생성한다.
2. account·cbi·onboarding과 calendar·schedule을 연결한다. 온보딩 중 분석 허용 조건을 먼저 테스트한다.
3. checkin·recovery를 완성하고 적격 7일·결측일·컨디션 변경을 검증한다.
4. recommendation·캘린더 승인/되돌림·재시도를 연결한다.
5. home·reports·safety·subscription 체험 표시·탈퇴를 완성한다. 삭제 경계는 마지막까지 미루지 말고 각 기능 PR부터 계약과 테스트를 둔다.

미확정인 회복 산식/초기 7일 제외 규칙·일정 가중치/종일 일정·컨디션 추천 임계값·LOW 2주 연속/재노출·4주 백분위 최소 표본·동의 선택 정책은 [검토 결과](검토결과.md)와 API의 결정 항목을 따른다. 폴더 구조 설계가 이 정책들을 확정한 것은 아니다.

## 10. 검증 기준

- 순수 domain/policy 테스트: 계산 경계·결측일·서울 날짜·교란 요인·상태 전이.
- 기능 application/API 테스트: 소유권·동의·응답 형식·재시도·버전 검증.
- MySQL 통합 테스트: ERD의 FK/UK/CHECK·Flyway·JPA validate·트랜잭션·동시 승인.
- experience 흐름 테스트: 중간 실패·부분 성공·온보딩 순서·건강 삭제/탈퇴·외부 타임아웃 복구.
- 구조 테스트: feature→experience, 기능 간 Repository/Entity import, shared→기능, integration→기능 application을 금지한다. ArchUnit 같은 검사 도구는 실제 개발 시작 시 별도 도입 검토하며 이번 설계에 의존성을 추가하지 않았다.

문서 검증은 모든 API/테이블이 빠짐없이 책임에 매핑됐는지 확인하는 것이며, 실제 서버 테스트 통과나 새 구조 구현 완료를 의미하지 않는다.
